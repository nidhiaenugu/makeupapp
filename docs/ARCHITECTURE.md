# Architecture

## The shape of it

```
  src/app/            Next.js App Router: pages + API routes
      │                 (thin — parses input, calls the engine, renders)
      ▼
  src/lib/engine/     The matching engine
      │                 Pure functions. No React, no Next, no I/O.
      ▼
  src/lib/data/       CatalogProvider interface
      │                 One seam between the app and wherever data lives.
      ▼
  src/lib/domain/     Types, taxonomy, zod schemas
                        The shared vocabulary everything else imports.
```

Dependencies point one way only: `domain` knows nothing, `engine` depends on `domain`, `data` depends on `domain`, and `app` depends on all three. Nothing lower ever imports from something higher.

## Three decisions worth explaining

### 1. The engine is a pure function

`recommend(products, profile, options)` takes arrays and objects and returns objects. It performs no I/O, reads no globals, and imports nothing from React or Next.

This buys three things:

- **Testability.** 87 tests run in under a second with no mocking, no test server and no fixtures beyond plain objects.
- **Reuse.** The same code backs the web UI, the REST API and any script you write. A CLI or a batch job needs no adaptation.
- **Portability.** Moving to a different framework means rewriting `src/app/` and nothing else.

The cost: the engine scores the whole catalog in memory on each call. At 86 products that is microseconds. Past roughly 10,000 products you would want to pre-filter in the data layer before scoring — `CatalogProvider` is the right place to add that, and the engine's signature would not change.

### 2. Hard filters are separate from scoring

Two mechanisms, deliberately:

**Hard filters** (`engine/filters.ts`) remove a product from consideration. The test for belonging here: *would a user be actively upset to see this at all?*

- Outside the categories they asked about
- Over their stated budget ceiling
- Fails a preference they marked as a dealbreaker
- Contains an ingredient on their avoid list
- Stronger than their stated experience level
- A level-3 active when they said their skin is reactive

**Scoring** (`engine/scoring.ts`) ranks everything that survives. A slightly-wrong finish or a formula aimed at a different skin type is a *worse* match, not an unacceptable one.

Collapsing these into one weighted score would be simpler and wrong: an allergen given a very low weight is still a product that can land in someone's results. Filtering is a promise; scoring is a preference.

### 3. Explanations are generated by the scorer, not written afterwards

Each scoring factor returns both a sub-score *and* the sentence justifying it, carrying the actual points contributed. The explanation is a by-product of the calculation rather than a separate description of it, so the two cannot drift apart. If a factor's weight changes, the number quoted in the UI changes with it automatically.

This is also why negative reasons exist as first-class output. A product that treats acne but worsens dryness surfaces that on the card. A recommender that only ever tells you good news is not one you can calibrate your trust against.

## The scoring model

Seven factors, each producing a 0–1 sub-score multiplied by its weight, summed and scaled to 0–100. Weights live in one exported table (`WEIGHTS` in `engine/scoring.ts`) and a test asserts they sum to exactly 1.

| Factor | Weight | Notes |
| --- | --- | --- |
| `concerns` | 0.34 | The dominant factor — it's why the user is here |
| `typeFit` | 0.20 | Skin type, or hair type/texture/porosity/scalp |
| `preferences` | 0.14 | Soft preferences only; must-haves are already filtered |
| `budget` | 0.10 | Distance from the preferred tier |
| `aesthetic` | 0.09 | Finish, coverage, texture |
| `shade` | 0.08 | Best shade confidence + how well the range covers them |
| `curation` | 0.05 | Editorial weight, low enough to only break ties |

**Concern ordering.** Concerns are weighted `1 / (1 + index × 0.35)`, so the first counts roughly 1.0, the second 0.74, the fourth 0.49. Gentle enough that a fourth concern still matters.

**Aggravation.** Subtracts at half the rate a match adds. Making one concern worse should sting without cancelling out treating two others well.

**Neutral defaults.** An unknown field scores 0.6, not 0. A user who skips the hair questions should not have every hair product penalised — absence of information is not evidence of a bad fit.

## Shade matching

Depth carries 70% of confidence, undertone 30%. A foundation two shades too light is obvious across a room; a slightly-off undertone reads as mild warmth mismatch.

Undertone compatibility is a lookup table rather than an equality check, and it is deliberately asymmetric — olive skin usually looks better in a neutral than in a cool, and neutral is a decent stand-in for both cool and warm.

**Depth proximity never flattens to zero.** An earlier version clamped it at three steps' distance, which meant that when every shade in a range was far from the user, "closest" became whichever happened to be first in the array — a deep-skinned user could be handed the *lightest* shade in a pale range. The decay now keeps a small monotonic tail so ordering stays meaningful at any distance. `tests/shade.test.ts` pins this.

Separately, `rangeCoverage` scores whether the range *as a whole* serves the user. A ten-shade range stopping at medium depth is a worse product for a deep-skinned user even if its darkest shade is technically "closest".

## Result diversification

Raw score ordering produces eight cleansers and no moisturiser when someone's top concern is acne. `capPerType` caps how many products of one type appear in the head of the results, then appends the overflow rather than discarding it — so a user who wants more foundations still finds them further down.

This means `recommendations` is **not** globally sorted by score. That's intentional and tested: `maxPerType: 0` gives you strict score order, and the highest-scoring product leads either way.

## Data layer

`CatalogProvider` is four methods: `all()`, `byId()`, `query()`, `brands()`. The bundled `JsonCatalogProvider` reads three JSON files, validates them against the zod schema once at module load, and indexes by id.

Validation at load is deliberate: a malformed catalog fails loudly at startup rather than producing quietly wrong matches. The same schema runs in CI through `npm run validate:catalog`.

To swap the source, implement the interface and return it from `getCatalogProvider()` in `src/lib/data/index.ts`. That function is the only place in the codebase that names a concrete provider.

## Taxonomy as the single source of truth

`src/lib/domain/taxonomy.ts` declares every controlled vocabulary — categories, product types, concerns, preferences, scales. The zod schemas derive their enums from it, the quiz renders its options from it, the validator checks against it, and the API exposes it at `/api/meta`.

Adding a concern is one entry in the `CONCERNS` array. It immediately appears in the quiz, becomes valid in the API, gets checked by the catalog validator, and starts participating in scoring. Nothing else needs touching.

## State and persistence

There is no backend user store. Profiles and saved products live in `localStorage`, re-validated with zod on every read — a schema change or a hand-edited value falls back to a clean profile instead of crashing.

The results page fetches from `/api/recommendations` rather than importing the engine, which keeps the catalog out of the client bundle and means the page exercises the same endpoint third-party clients use. The product page does the opposite — it imports the scoring module to grade a single already-fetched product, since that costs a few kilobytes and avoids an endpoint existing for one card.

## Testing

`tests/` covers the engine and the data, not the UI:

| File | Covers |
| --- | --- |
| `scoring.test.ts` | Weight invariants, concern ordering, aggravation, reason ordering |
| `filters.test.ts` | Every exclusion rule and its boundaries |
| `shade.test.ts` | Depth/undertone weighting, range coverage, honest messaging |
| `recommend.test.ts` | End-to-end against the real catalog; routine ordering and safety |
| `catalog.test.ts` | Semantic data integrity the schema can't express |

The catalog tests are the ones that catch real mistakes: a concern no product treats, a product marked pregnancy-safe that contains a retinoid, a "fragrance-free" product listing an essential oil as a hero ingredient.

## Known limits

- **Scoring is linear.** No interaction terms — the engine won't learn that niacinamide plus a specific SPF is unusually good together.
- **No feedback loop.** Nothing learns from what users actually buy or keep. That would need a backend and a real user store.
- **In-memory scoring.** Fine to low thousands of products; beyond that, pre-filter in the provider.
- **The catalog is a sample.** 86 products, curated to exercise the engine, not to be a shopping index.
